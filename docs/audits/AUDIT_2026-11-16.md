## 4. Findings

Fields: **Type** · **Severity** (harm if it happens) · **Priority** (P0 now, P1 before handoff 02, P2 inside an existing handoff, P3 later) · **Confidence**. Effort is split into implementation and verification, with the assumption behind it.

### A-001. Sign-up fails when two emails share a local part
- **Type:** demonstrated defect. **Severity** high. **Priority** P1. **Confidence** high.
- **Evidence:** `supabase/migrations/20260831000000_baseline.sql:43-46` sets `username` to `split_part(new.email, '@', 1)`; line 46 handles only `on conflict (id)`; line 59 makes `username` unique. `src/app/login/page.tsx:37` sends no username. Reproduced on the local stack inside a rolled-back transaction: the second insert raised `duplicate key value violates unique constraint "profiles_username_key"`.
- **Counterevidence checked:** no client code supplies a unique username; `tests/e2e/local-supabase.spec.ts` signs up one user only; pgTAP has no trigger test.
- **Exposure and who is affected:** any new user whose email local part equals an existing username cannot create an account, and the error also reveals that the username exists. Whether strangers can sign up in production was not assessed at audit time. **Update, § 8:** sign-up is open, but with the default SMTP only organization members can confirm an account, so exposure is limited until custom SMTP is enabled.
- **Fix:** the trigger retries with a short random suffix on a username conflict. → **AUD-01**.
- **Effort:** implementation 1 hour, verification 1 hour, assuming a `create or replace function` migration with no data change.
- **Acceptance test:** two sign-ups, `sam@a.test` then `sam@b.test`, both succeed and get different usernames.
- **Blocks:** opening sign-ups to more than a few people, because failures grow with the user count.

### A-002. The shared `releases` cache trusts rows supplied by clients (`AUD-SEC-1`)
- **Type:** demonstrated defect, security. **Severity** high. **Priority** P1. **Confidence** high for the policy; medium for one consequence that was not tested in a browser.
- **Evidence:** `baseline.sql:151-157`: any authenticated user may insert into, and update, the shared table. Handoff 02 item 10 removes UPDATE only, and its `ignoreDuplicates` change then makes the first writer of a row permanent. Further mechanics are held privately.
- **Counterevidence checked:** RLS on the per-user tables is sound, so no user's private rows are reachable this way. pgTAP `rls_test.sql` asserts the current permissive behaviour, it does not forbid it.
- **Exposure and who is affected:** every signed-in user who views a release another account wrote first. Requires an authenticated account. **Update, § 8:** with the default SMTP only organization members can confirm an account today. Custom SMTP must stay off until this finding is fixed.
- **Fix:** (a) format and length constraints on every `releases` column → **AUD-02**. (b) only the server writes `releases`, from MusicBrainz data → **AUD-08** (Q-02 answered yes).
- **Effort:** AUD-02: 1 hour + 1 hour. AUD-08: 4 hours + 3 hours, assuming a test stub for MusicBrainz is needed in e2e.
- **Acceptance test:** as an authenticated user, an insert or update on `releases` through the Data API is refused; logging an album never seen before still works.
- **Blocks:** handoff 04, because public profiles and reviews multiply who sees shared rows.

### A-004. No backup of production data exists
- **Type:** risk, confirmed by Vishnu (Q-03). **Severity** high. **Priority** P0. **Confidence** high.
- **Evidence:** Supabase Free makes no automatic backups (`docs/EXTERNAL-SOURCES.md:63`). The only dumps ever taken are schema-only (Q-03). The restore drill (handoff 01 task 13) has not started. Nothing schedules a recurring backup. `docs/RUNBOOK.md:11` records that the caller of `keep_alive` is unknown. Supabase's pausing page (read 2026-11-16) says a paused Free project can be restored for up to 1 year.
- **Counterevidence checked:** RUNBOOK and STAGING have no backup routine. CI artifacts are not an option: the repository is public.
- **Exposure and who is affected:** every user's diary, reviews and lists. A bad migration, a mistaken delete or a lost project is unrecoverable today.
- **Fix:** dump roles, schema and data before every production migration and monthly, into `C:\earwrm-backups` (not synced, outside the repo) plus an encrypted copy Vishnu controls; then run the drill. → **F-2** now; the routine is written into handoff 01 task 13 by **AUD-07**.
- **Effort:** first dump 30 minutes; routine and drill are already scoped in D2.
- **Acceptance test:** a dump dated before the next production migration exists in both places, and the D2 drill restores it into a disposable local stack with matching row counts.
- **Blocks:** every production migration (AUD-01, AUD-02, AUD-08, handoff 02a) because none can be undone without it.

### A-005. Writes are unordered and rollback restores too much
- **Type:** demonstrated defect, by code reading; not reproduced. **Severity** medium. **Priority** P2. **Confidence** medium-high.
- **Evidence:** `src/lib/store.tsx:273-291`: every write is started with `void` and nothing orders two writes to the same row. Rollbacks restore a whole-array snapshot (`:372`, `:412`), which also discards later changes that saved. Two-step writes share one `revert`: entry then queue-clear (`:371-381`), list then seed item (`:427-439`); if the second step fails the first is shown as not saved although it is in the database. The rating control fires `onChange` on every half-star while dragging (`src/components/ui.tsx:93`, `:106`), and each one is an upsert. Handoff 03 task 2 says to keep "the *current* optimistic and rollback behavior".
- **Counterevidence checked:** failures do show the "didn't save" dialog, so this isn't silent on failure; the silent case is two successful writes landing out of order. Handoff 02 item 1 covers drag-reorder only.
- **Exposure:** the screen and the database can disagree until reload, with no error. This is the same class as the earlier silent-save bugs.
- **Fix:** serialize mutations per resource, roll back by refetching that resource, and do two-step writes in one SQL function. → amend handoff 03 task 2 and handoff 02 item 1 (**AUD-07**, Q-04 approved).
- **Effort:** inside handoff 03a: 4 hours + 3 hours.
- **Acceptance test:** an e2e test delays the first of two rating writes so it arrives second; after reload the diary shows the second rating.
- **Blocks:** nothing now. Carrying it into the data layer would bake it into every later feature.

### A-009. The MusicBrainz proxy is open and unbounded
- **Type:** demonstrated gap. **Severity** medium. **Priority** P2. **Confidence** high.
- **Evidence:** `src/proxy.ts:37` leaves `/api/mb/*` public. `src/app/api/mb/search/route.ts:21` has no length cap on `q`. `src/lib/rateLimit.ts:35-38` queues without bound and only per server instance. `src/lib/musicbrainz.ts:32`, `:377`, `:399` set no timeout. The `mbid` parameter is unvalidated (handoff 02 item 11). MusicBrainz requires at most one call per second per client and a meaningful User-Agent (API page, read 2026-11-16). Wikimedia allows 200 requests a minute with a compliant User-Agent (rate-limits page, edited 2026-11-08).
- **Counterevidence checked:** aborted requests leave the queue; caches are bounded at 500 entries; the upstream host is fixed, so this is not a general server-side request forgery.
- **Exposure:** anyone can consume the instance's MusicBrainz budget or Vercel's free allowance, or get earwrm's User-Agent blocked. The outcome is a pause or a block, not a bill.
- **Fix:** covered by 02 item 11, 03b and 03 § 5b. Amendment: 03b names upstream timeouts and a bounded queue (**AUD-07**).
- **Effort:** inside 03b: 1 hour + 1 hour.
- **Acceptance test:** an upstream that never answers produces a 502 within the timeout; a 2,000-character query is rejected with 400 and makes no upstream call.
- **Blocks:** nothing now.
